Sem o `x-init`, quem fechasse os filtros no celular e chegasse a >=640px (girar o aparelho, alargar a janela) via o painel continuar fechado até clicar de novo no `` — o `` fica sempre visível (não é `sm:hidden`) justamente pra sobrar esse controle manual se o JS falhar ao carregar. Sincronizar o atributo `open` resolve na fonte, porque `open` é o estado real do disclosure. `x-init` roda de qualquer forma no load — inclusive no desktop — então o HTML nasce SEMPRE fechado no mobile e o próprio `x-init` reabre no desktop (>=40rem) antes da primeira pintura visível. O server-render nunca nasce com `open`, com ou sem filtro ativo (issue #155). A #145 media só o caminho COM filtro; concluiu que sem filtro "nasce aberto — não há custo de espaço a evitar". Há custo, e é o caso que mais paga: sem filtro é a entrada padrão, e a 375x812 com dados de `seed_dev` o painel aberto empurrava o primeiro cartão ~1,58 viewport abaixo da dobra. O `` carrega o resumo do recorte, então o painel fechado não esconde qual filtro está aplicado. Escuta os dois sinais de propósito: `change` da media query é o correto e suficiente num navegador de verdade; `resize` cobre ambientes que mudam a viewport sem notificar a media query (a emulação de viewport por CDP, usada pelos testes de navegador, é um deles). O handler só lê `matches` e atribui um booleano — repetir em cada resize não custa nada. {% endcomment %}
